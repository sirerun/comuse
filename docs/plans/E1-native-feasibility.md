# E1 -- Native feasibility and ten-lane spike

fidelity: executable
Acceptance: the landed spike bundle has reproducible ABI/lifetime, AX identity/read/write, scope/ownership/cleanup, semantic-only, JSON/protocol and host-launch evidence on a controlled Mac, with an explicit supported/unsupported matrix and no production-readiness claim.

This is the only fully decomposed horizon. Its probes are bounded experimental code under `spikes/`, not a public runtime implementation. Test doubles stay in explicit test packages; unqualified methods fail explicitly. No mutation is exposed to a normal model client. Actual native input tests run only through the integrated fixture-only safety gate, never through competing standalone worker executables.

The shared seam is a small separate merge candidate. The ten lane branches form one explicitly speculative spike integration candidate after that seam lands: no worker branch is a release or bypasses review. This lets branches develop concurrently without treating branch-local success as delivery. A common preflight and the final shared review/merge/landed chain cover every listed coding task. Intermediate verification is scoped branch evidence; the integrated candidate is reverified after all changes.

## Acceptance and stop conditions

Native verification is serialized on the approved GUI desktop. A controlled fixture and known target identity are mandatory before read/input experiments. Preflight inventories signing/TCC authority; T1.6 supplies operator-owned prerequisites. Source-only work can proceed independently, but a native verification row cannot pass from mocks or an unavailable desktop. Builds remain on hold above the load ceiling or without the shared lease.

T1.31 must record the actual architecture, macOS, Go/Swift/Xcode/SDK/deployment settings, permission-owning executable/bundle and CLI/stdio launch paths, fixture revision, dispatch/verification/cleanup results and reproduction artifacts. Test the proposed macOS 14 compilation baseline; runtime behavior on macOS 14 remains unqualified without an actual supported test host. If minimum-OS runtime or signed-launch evidence is unavailable, explicitly limit the feasibility conclusion and carry the release blocker forward. Do not silently broaden or lower the promised support matrix.

Any failure involving native identity, callbacks, cancellation, ownership, protected contexts, or focus is a stop for that path. Record the gap; continue only independent safe source/contract work. Accepted review findings create new stable fix, affected-verification and re-review task rows; do not mark negative review complete. A public production implementation is expanded only from the landed feasibility findings, never by promoting a spike flag into a support claim.
